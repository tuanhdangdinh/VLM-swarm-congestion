# Decompose by cluster to recover coverage

The coverage regression has the same shape as a documented failure. Under grounding-first prompting, cluster coverage fell from 0.64 to about 0.47. That matches the "count bias" SATA-Bench measured in 27 LLMs: asked for a set, models pick too few and leave items out. Prompt rewording barely helps. Telling the model the count (**+20.95 exact-match points**) or splitting the question into one sub-question per item (**+12.53%**) helps a lot ([SATA-Bench](https://arxiv.org/html/2506.00643v3)). SATA used text-only multiple-choice questions, so the transfer to our image-plus-state prompt is an untested inference. A pick-one menu also caps the answer at one choice by format alone. The practical fix is for M3 to cluster jams first and ask for one choice per cluster, through a JSON schema whose required keys are the cluster ids. That forces an entry for every cluster. Per-cluster abstention becomes the remaining coverage metric. It also shrinks each menu to 2–3 options, which should weaken the first-slot and robot_1 priors (also untested). When the verifier rejects a choice, the retry should name the uncovered cluster and list its admissible alternatives; in one 2026 study that field carried nearly all the repair gain (14→36 of 50) ([Ray & Goyal](https://arxiv.org/abs/2607.14167)). ER-2 has no temperature control, so voting has to draw diversity from prompt and option permutations. Logit debiasing, SATA's Choice Funnel included, needs logprobs that ER-2 and Claude do not expose. For the bench, driving research shows that adding a few perturbed follow-up states to each logged scene lifts offline-to-closed-loop rank correlation to r = 0.89 (NAVSIM pseudo-simulation, snippet-level) ([PMLR](https://proceedings.mlr.press/v305/cao25a.html)). IR-SIM, a CPU-only multi-robot diff-drive simulator with a built-in top-down renderer, is the cheapest way to make those states without spending 55 GPU-minutes per Isaac episode ([arXiv:2606.08729](https://arxiv.org/abs/2606.08729)). On novelty, the scan found no paper since mid-2026 with an overhead-camera VLM choosing warehouse congestion strategies, and no new coordinator that handles multi-cluster scenes. CoRL/IROS 2026 lists and a full Oct–Nov arXiv crawl were not checked. The closest overlaps are architectural: CoPlanVLM and a verifier-mediated multi-LLM planner.

## Per-cluster schemas turn coverage from a model habit into a guarantee

SATA-Bench is the anchor here, and its message is blunt. The best of 27 models reaches only **41.8% exact match** on select-all-that-apply questions. Reasoning models do not reduce count bias. Option-symbol changes, few-shot examples and going option by option give no consistent gain ([arXiv](https://arxiv.org/abs/2506.00643)).

A second 2026 paper shows why a looser "list everything that applies" format will not rescue us. Models judge whether a single candidate belongs to a set **+0.29 to +0.34 F1** better than they enumerate the set. **Omission is the dominant error**: models catch planted over-inclusions 6–7× more often than planted omissions ([Judging Is Not Enumerating](https://arxiv.org/abs/2608.01000)). Closest-pair-yield-only is exactly an omission error.

The fix is therefore structural. Every provider now supports enum or JSON-schema constraints; Gemini also supports `propertyOrdering` ([Gemini docs](https://ai.google.dev/gemini-api/docs/structured-output)). Make the response an object keyed by M3's cluster ids. Each value is an enum of that cluster's feasible option ids, plus an explicit `none_feasible` member. The syntax then guarantees an entry for every cluster. One metric consequence follows. Under this schema, "coverage" reduces to the per-cluster abstention rate (how often `none_feasible` is chosen when a feasible option exists). The bench must also score per-cluster choice quality. SATA's set metrics (Jaccard, exact match, signed count error CtDif) remain the right tools for any free multi-select comparison arm.

Garg et al.'s v2 paper is a precedent from multi-robot work. It splits large teams into k-means clusters with heuristic sub-leaders, and reach rate "drops significantly when only one leader is used" ([arXiv HTML v2](https://arxiv.org/html/2404.06413v2); the figure's numbers could not be extracted). This supports clustering in M3 and asking the VLM only for the per-cluster choice. *Inference:* SATA's gains were measured on text-only multiple-choice questions, so carrying them over to our image-plus-state prompt is untested.

The verifier loop should carry information the model cannot guess. In VeriHarness, adding admissible alternatives to rejection feedback lifted success from **14→36/50 and 8→29/50** on two small open models. Location and observed value alone stayed near baseline, and JSON vs. prose made no difference ([arXiv](https://arxiv.org/abs/2607.14167)). The evidence comes from TextWorld games, not robots. M3 already knows which clusters a decision leaves unaddressed, so "cluster B uncovered; feasible options for B are {…}" is a cheap, targeted re-ask with a hard cap of 2–3 calls and a deterministic per-cluster fallback.

For voting under ER-2's fixed temperature, plain exact-match majority over categorical labels is enough. Universal Self-Consistency ([arXiv](https://arxiv.org/abs/2311.17311)) adds an LLM-as-selector step. Secondary summaries say that step carries its own position bias and degrades on short answers; this is unverified, from search summaries ([2508.18395](https://arxiv.org/abs/2508.18395), S). Diversity can come from Dipper-style prompt variants ([arXiv](https://arxiv.org/abs/2412.15238)) combined with option permutations. *Inference:* vote per cluster, not per scene, and treat no-majority as an escalation to the fallback.

## First-slot and robot_1 priors need measurement, not more prompting

Vision-language models carry the same option-position bias as text models. Permuting the answer set is an effective attack on VLMs ([arXiv:2310.01651](https://arxiv.org/abs/2310.01651)). The bias **grows with task difficulty**: LLaVA-1.5-13B picks "A" about three times its true rate on hard items ([arXiv:2509.16805](https://arxiv.org/html/2509.16805v1)).

The mitigations measured so far subtract a bias vector from option logits. They need logits, and the gains on Qwen2.5-VL-7B were only +1.15 to +1.84. So for ER-2, Claude and gpt-4o without logprobs, the practical tool is still permutation.

Two pieces are new. First, a **label-free Permutation Bias Metric** (the inconsistency rate across answer orderings) turns our first-slot finding into a per-model number at 2–3× cost ([arXiv:2511.21709](https://arxiv.org/abs/2511.21709)). Second, an LREC 2026 study of 14 multimodal models found predictions shift with **modality order** (image before or after text) as well as answer order ([ACL Anthology](https://aclanthology.org/2026.lrec-1.716/), S). That suggests a third randomization axis we have not tried.

*Inference, untested in spatial VLM settings:* opaque option ids (for example `opt_k3` instead of robot-ordered labels) should remove the robot_1 prior at the token level. Per-cluster sub-menus should reduce slot competition. No public measurement exists of whether enum member order inside a JSON schema biases selection on Gemini or OpenAI. One permutation run on our bench would settle that.

## Since mid-2026, coordinators share our architecture but not our task

The scan found no paper since mid-2026 in our niche: an overhead-camera VLM detecting warehouse congestion and choosing a strategy that a symbolic grounder executes. **Every new coordinator found handles a single conflict or two robots.** Our multi-cluster weakness therefore looks like a gap in the literature as well as in our system, and is worth framing as a contribution. Caveat: CoRL/IROS 2026 accepted-paper lists and an Oct–Nov 2026 cs.RO/cs.MA arXiv crawl were not checked.

**CoPlanVLM** (Oct 2026) is the strongest new evidence for spatial scaffolding. An image overlay marking free space and obstacles, a task classifier that picks the planner and prompt, and role-assigning chain-of-thought reach **84.4% success vs. 50.0%** for the closest baseline, on TurtleBot 4 and Gazebo, with open code ([arXiv](https://arxiv.org/abs/2610.14341)). A snippet claims inter-robot collision avoidance happens after planning; that is unconfirmed. **Verifier-Mediated Multi-LLM Coordination** has the same proposer/geometric-verifier/feedback split as our M2→M3 gate, but for path planning, and its abstract gives no numbers ([arXiv](https://arxiv.org/abs/2610.12761)). A game-domain paper is a useful caution: an LLM picking from a skill menu matched but did not beat a behavior tree (**46.4% vs 51.5%**, not significant) ([arXiv](https://arxiv.org/abs/2606.20014)).

On the MAPF side, the LLM's role has moved from online solver to offline planner engineer. In **Late Autumn** (Koenig group, Nov 2026), coding agents patched a warehouse task-assignment and MAPF planner for **+22–60% throughput**, rediscovering corridor-exit priorities and local guidance. Some patches raised compute more than 100×, and the gains mostly vanished under outbound-heavy demand ([arXiv](https://arxiv.org/abs/2611.02391)). Reviewers will raise it, so a corridor-exit-priority rule baseline is the natural ablation. The scan found no 2026 paper using an LLM to guide CBS, PIBT or LaCAM online, and no MAPF-GPT successor. Spatial benchmarks agree that VLMs are unreliable at metric comparison among **same-category instances**, which is exactly the case of identical robots ([SpatialQuery](https://arxiv.org/abs/2608.01709v1)). That supports giving M2 explicit distances in text.

## A text-only open-loop bench needs a cheap counterfactual tier

Our 187-item bench is an **open-loop bench** in the driving sense. It shows whether the VLM picks a feasible, oracle-agreeing strategy for a logged state. It does not show whether congestion clears faster. Driving research has already shown the danger: open-loop and closed-loop nuPlan scores were misaligned and, in places, negatively correlated ([arXiv:2306.07962](https://arxiv.org/abs/2306.07962), S).

NAVSIM's pseudo-simulation is the fix to borrow. It scores the logged state, then about 12 perturbed follow-up states weighted by closeness to the planner's choice. Over 83 planners this reaches **r = 0.89** with closed-loop scores, against 0.83 for the best open-loop metric, using about 13 inferences instead of 80 per scenario ([arXiv:2506.04218](https://arxiv.org/abs/2506.04218); code [navsim](https://github.com/autonomousvision/navsim), S). Naive replay also penalizes a new model whose choice would have changed the outcome. The logged result therefore scores a new VLM only on items where it picks the logged strategy. A NeurIPS 2026 "commit-point" estimator formalizes that limit ([poster](https://neurips.cc/virtual/2026/168256), S; [blog](https://tianpan.co/blog/2026-05-22-shadow-replay-punishes-models-that-change-the-conversation), B).

The world model that produces those follow-up states should be a 2D simulator, not Isaac. Isaac runs **slower than real time** (one forum report gives RTF ≈ 0.14 with three robots) ([NVIDIA forum](https://forums.developer.nvidia.com/t/how-can-we-get-simulation-time-close-to-real-time/307676), B).

**IR-SIM** is the best fit. It supports diff-drive kinematics, multi-robot ORCA/RVO behaviours, YAML scenarios that LLM agent skills can compose, and a top-down matplotlib renderer. It claims to run "several hundred times faster", but the baseline is unnamed, and no ROS 2 bridge was found in the paper's table or README ([arXiv](https://arxiv.org/abs/2606.08729); [repo](https://github.com/hanruihua/ir-sim), V). **Flatland** keeps Nav2 in the loop: its ROS 2 branch targets Humble through Rolling and runs headless and faster than real time. Its README warns that ROS nodes may fall behind, so lock-step clocking, which FastSwarmSim also uses, matters ([repo](https://github.com/avidbots/flatland/tree/ros2), V).

The vision question is open, not settled. EmbodiedBench found that removing vision cut low-level task scores by 40–70% but **barely affected high-level planning** ([arXiv:2502.09560](https://arxiv.org/abs/2502.09560), S). That predicts adding images to a strategy-selection bench may move scores little, but it should be tested.

For images, no turnkey "pose log → overhead frame" tool exists. Reusing M1's `annotation.py` on a blank map raster is the lowest-risk renderer. It also removes the real-frame refusal confound, but it introduces a synthetic-to-real gap that has to be disclosed (*inference*).

## Borrow Inspect's cache keys and add a prereg guardrail rather than switching frameworks

The custom bench already has most of the ideas worth having: a prompt-hash cache, SHA-256 run configs and git-tagged preregistrations. Three gaps remain. The first is explicit cache-key scope. Inspect AI hashes model, base URL, full messages, generate config and tools, and adds user-defined `scopes`, so the prompt version, shuffle seed and prereg tag can be put into the key deliberately ([docs](https://inspect.aisi.org.uk/caching.html)). Inspect's `eval-retry` skips sample reuse when it detects a dataset shuffle, so a per-sample seeded permutation is the safe pattern if we ever port ([logs docs](https://inspect.aisi.org.uk/eval-logs.html)). *Inference, untested:* passing images by file path could let a re-rendered frame hit a stale cache entry. The second gap is recording the **git commit and package versions** in every run JSON. The third is a **cross-run ledger** covering variant, model, n, cost, metric and prereg tag.

For statistics, Miller's error-bars paper recommends inference on per-question paired differences and a power analysis before spending credits ([arXiv:2411.00640](https://arxiv.org/abs/2411.00640)). SciPy's `bootstrap(paired=True)` gives paired BCa intervals. statsmodels adds the exact McNemar test, but it is not yet in the project requirements. The 2026 prereg literature adds a usable protocol: name "the next eligible model release" as the held-out confirmatory model. Across 20 models this blocked p-hack transfer in about **73%** of cases ([arXiv:2606.27687](https://arxiv.org/abs/2606.27687)).

## Conclusion

The coverage regression most likely comes from the **question format**, not from weak VLM reasoning that a better model would fix. A single-pick menu caps the answer at one choice by construction. The set-selection literature predicts that even multi-pick formats default to omission, though that evidence is text-only and untested on our prompts. That changes the research claim. The defensible contribution is the split of responsibilities: M3 owns the cluster structure and feasibility, and the VLM owns only within-cluster preference. The bench should evaluate exactly that preference, with position bias measured as a per-model number rather than inferred.

The broader implication is about validity. Every ranking from the text-only bench is an open-loop ranking until a counterfactual tier exists. A CPU 2D simulator is now cheap enough that "bench vs. closed-loop rank correlation" can become a reported number, not a caveat. The niche itself still looks open: the scan found no 2026 coordinator that handles multi-cluster congestion. Several items above rest on abstracts or snippets, notably NAVSIM's figures, the commit-point estimator and CoPlanVLM's collision handling. Read their full texts before citing them in a paper.

## Try next (prioritised)

1. **Per-cluster schema in M3 → M2.** M3 clusters jams. The response schema has required cluster-id keys with enum values of that cluster's feasible options plus `none_feasible`. Rerun the 187-item replay and report per-cluster abstention rate, choice quality, feasibility, and CtDif for any free-select arm ([SATA-Bench](https://arxiv.org/abs/2506.00643)).
2. **Admissible-alternatives retry.** On an uncovered cluster or an infeasible pick, re-ask once with the cluster id, the reason, and the feasible options. Cap at 2–3 calls, then use the deterministic per-cluster fallback ([2607.14167](https://arxiv.org/abs/2607.14167)).
3. **Bias as a number.** Run 2–3 cyclic option orders plus opaque option ids, and one image/text-order swap, and report the permutation-inconsistency rate per backend ([2511.21709](https://arxiv.org/abs/2511.21709)). For ER-2, do exact-match majority voting per cluster over permutation and prompt variants.
4. **Text-only vs. synthetic-image arm.** Render bench states with M1's `annotation.py` on a map raster. That tests EmbodiedBench's "vision barely matters for high-level choice" prediction and avoids the real-frame refusal confound.
5. **IR-SIM counterfactual tier.** Port one head-on and one multi-cluster scene, implement yield/reroute/backup as simple controllers, and score each strategy's follow-up state NAVSIM-style.
