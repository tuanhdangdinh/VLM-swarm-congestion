# Verification, Grounding, and Repair Layers Around LLM/VLM Robot Planners (2022–2026) — the Propose-Verify-Repair Pattern

Scope note: notes gathered 2026-10-01 via web search over arXiv/venue pages. Papers with arXiv IDs of the form 26xx.* are 2026 preprints; venue status for those is often not yet settled and is flagged where unknown. Items marked "(from author's prior knowledge, ID unverified this session)" have canonical, widely cited arXiv IDs but were not independently re-fetched in this session.

## Key Question 1: Canonical propose-then-verify architectures (LLM+PDDL, TAMP, affordance gating, constrained decoding, VLM equivalents)

### Takeaway
The 2022–2024 canon splits into four families: (a) LLM-as-translator feeding a sound classical planner/validator (LLM+P, LLM-DP, ViLaIn, LaMMA-P), (b) LLM-as-proposer gated step-wise by learned feasibility/affordance scores (SayCan, Text2Motion, Grounded Decoding — the constrained-decoding branch), (c) LLM/TAMP hybrids where a geometric or temporal-logic checker vets LLM output (AutoTAMP, Text2Motion, SayPlan's scene-graph simulator), and (d) the generate-test-critique position crystallized as "LLM-Modulo" (Kambhampati et al.). VLM equivalents (ViLaIn, ReplanVLM, VeriGraph) arrived 2023–2024 and reuse the same skeleton with scene perception replacing text state.

### Cited Findings
- **SayCan** ("Do As I Can, Not As I Say: Grounding Language in Robotic Affordances", CoRL 2022, arXiv:2204.01691) scores each LLM-proposed skill by the product of the LLM's usefulness probability and a learned value-function affordance (can the skill succeed here?), so infeasible steps are gated out before execution — [PMLR v205](https://proceedings.mlr.press/v205/ichter23a/ichter23a.pdf)
- **Grounded Decoding** (NeurIPS 2023, arXiv:2303.00855) generalizes SayCan to the token level: it "jointly decodes the token probability of an LLM and token probabilities from token-conditioned robotic functions, such as affordance functions..., safety functions, or more"; action sequences must be high-probability under both the LM and the grounded model. Demonstrated in simulated tabletop rearrangement, Minigrid 2D maze, and real-world kitchen mobile manipulation — [grounded-decoding.github.io](https://grounded-decoding.github.io/); [paper PDF](https://arxiv.org/pdf/2303.00855)
- **LLM+P** (arXiv:2304.11477, 2023): LLM translates natural language to a PDDL problem, a classical planner solves it, LLM translates the plan back — soundness comes entirely from the symbolic planner (from author's prior knowledge, ID unverified this session) — [arXiv](https://arxiv.org/abs/2304.11477)
- **LLM-DP** ("Dynamic Planning with a Large Language Model", arXiv:2308.06391, 2023): neuro-symbolic agent where the LLM supplies belief about predicates and a symbolic planner produces the action sequence in Alfworld (from author's prior knowledge, ID unverified this session) — [arXiv](https://arxiv.org/abs/2308.06391)
- **AutoTAMP** is "Autoregressive task and motion planning with LLMs as translators and checkers," ICRA 2024 (arXiv:2306.06531): LLM translates to Signal Temporal Logic for a formal TAMP solver rather than planning directly, with syntactic/semantic re-prompting loops — [survey citation](https://arxiv.org/html/2505.05762v1); [arXiv](https://arxiv.org/abs/2306.06531)
- **Text2Motion** converts natural-language instructions to feasible plans by verifying geometric feasibility of skill sequences with learned Q-functions; published in Autonomous Robots, Nov 2023 (arXiv:2303.12153) — [ResearchGate mention](https://www.researchgate.net/publication/388495284_Planning_with_Vision-Language_Models_and_a_Use_Case_in_Robot-Assisted_Teaching); [arXiv](https://arxiv.org/abs/2303.12153)
- **SayPlan** (CoRL 2023, arXiv:2307.06135) grounds LLM planning in 3D scene graphs: semantic search for task-relevant subgraphs, integrated classical path planner, and "an iterative replanning pipeline that refines the initial plan using feedback from a scene graph simulator to correct infeasible actions" — [arXiv](https://arxiv.org/abs/2307.06135); [CoPAL related-work description](https://arxiv.org/html/2310.07263v3)
- **LLM-Modulo** ("Position: LLMs Can't Plan, But Can Help Planning in LLM-Modulo Frameworks", ICML 2024 position paper, arXiv:2402.01817): a "generate–test–critique" loop interposing a bank of external critics after every candidate plan; "if any critic returns FAIL, feedback is compiled into a back-prompt by a metacontroller" for the next LLM iteration — [arXiv html](https://arxiv.org/html/2402.01817); [overview](https://www.emergentmind.com/topics/llm-modulo-framework)
- A critical review notes LLM-Modulo's "never output any fallacious output" guarantee is overclaimed "because critic completeness is not established" — the critic bank is never shown to encode every correctness-relevant constraint — [EmergentMind overview](https://www.emergentmind.com/topics/llm-modulo-framework)
- **VLM equivalent (symbolic side)** — **ViLaIn** ("Vision-Language Interpreter for Robot Task Planning", ICRA 2024, arXiv:2311.00967) generates PDDL problem descriptions from linguistic instructions plus scene observations by chaining an open-vocabulary detector, a captioning model, and an LLM prompted with the full symbolic action model, "with optional planner-feedback retries to correct errors" — [arXiv PDF](https://arxiv.org/pdf/2311.00967); extended to bimanual TAMP in "Grounded Vision-Language Interpreter for Long-Horizon Bimanual Task and Motion Planning" (arXiv:2506.03270) — [arXiv](https://arxiv.org/pdf/2506.03270)
- **VeriGraph** ("Scene Graphs for Execution Verifiable Robot Planning", arXiv:2411.10446) uses VLM-derived scene graphs to verify executability of generated plans — [arXiv](https://arxiv.org/pdf/2411.10446)
- **Multi-agent PDDL**: **LaMMA-P** ("Generalizable Multi-Agent Long-Horizon Task Allocation and Planning with LM-Driven PDDL Planner", ICRA 2025, arXiv:2409.20560) combines LLM task decomposition/allocation across heterogeneous robots with a PDDL planner for soundness — [arXiv PDF](https://arxiv.org/pdf/2409.20560)
- Pre-execution verification as its own module: **VerifyLLM** ("LLM-Based Pre-Execution Task Plan Verification for Robots", arXiv:2507.05118) "combines formal LTL representations with LLM-based reasoning to identify inconsistencies in robot action plans" before execution — [arXiv PDF](https://arxiv.org/pdf/2507.05118); **VeriPlan** (arXiv:2502.17898) integrates a model checker with LLM planning for end-user planning tasks — [arXiv PDF](https://arxiv.org/pdf/2502.17898)
- 2026 synthesis of the whole pattern: **EvoPlan** ("Evolutionary Neuro-Symbolic Robot Planning with Spatio-Temporal Guarantees", arXiv:2607.06724) runs "an evolutionary PDDL planner where an LLM proposes and repairs plans against a fixed PDDL problem, with programmatic validators deciding which ones survive" — the closest published analogue to a proposer-vs-auditor survival framing — [arXiv html](https://arxiv.org/html/2607.06724)

### Inferences
- The field has converged on exactly the division of labor the thesis proposes: a generative model supplies semantic intent; a non-learned checker (planner, validator, value function, logic monitor) owns executability. What varies is the *granularity* of the gate (token, step, leg, whole plan) and *who performs the fix* (LLM re-prompt vs symbolic planner vs deterministic default).
- SayCan/Grounded Decoding gate *during* generation (the proposal never contains an infeasible step); LLM+P/AutoTAMP/ViLaIn verify *after* generation. The thesis M3 leg-by-leg audit of a complete VLM plan is structurally the post-hoc family, applied at leg granularity — a point in the design space these papers individually bracket but none occupies for multi-robot navigation.

### Gaps
- I found no published system where a *VLM proposes a complete multi-robot navigation plan* and a classical module audits it leg-by-leg; VLM-side verification work (ViLaIn, ReplanVLM, VeriGraph) is single-robot manipulation-centric.
- SELP ("Safe Efficient LLM Planner", believed arXiv:2409.19471, constrained decoding against LTL) is known to the author but was not re-verified this session; treat ID/venue as unconfirmed.

## Key Question 2: Plan REPAIR (minimal edits) vs reject-and-replan vs re-prompt-with-error-feedback — who does which, what do they measure?

### Takeaway
Almost all LLM-robotics systems choose *re-prompt-with-error-feedback* (the LLM itself repairs, guided by validator/simulator error messages); genuinely *minimal symbolic repair by a non-LLM module* is rare in the LLM era and is instead the classical-planning "plan stability" tradition (Fox et al. 2006). Measured quantities are almost always end-task success rate and sometimes number of refinement iterations — not edit distance from the original proposal.

### Cited Findings
- Classical anchor: **Fox, Gerevini, Long, Serina, "Plan Stability: Replanning versus Plan Repair" (ICAPS 2006)** introduced the *plan stability* metric and showed an LPG-based repair strategy "achieves more stability than replanning and can produce repaired plans more efficiently than replanning"; stability matters "where the safety of the executive... is a major consideration" — [Strathprints PDF](https://strathprints.strath.ac.uk/2776/1/strathprints002776.pdf); follow-ups include "Optimally Stable Plan Repair" — [Cambridge KER](https://www.cambridge.org/core/journals/knowledge-engineering-review/article/optimally-stable-plan-repair/DD03D400C759C63E399338832020F689) and "Plan commitment: Replanning versus plan repair" (EAAI 2023) — [ACM DL](https://dl.acm.org/doi/10.1016/j.engappai.2023.106275)
- **ISR-LLM** (ICRA 2024, arXiv:2308.13724): three steps — LLM translator to PDDL, LLM planner, then "iterative self-refinement" where a validator assesses the plan and the LLM refines it; reports "markedly higher success rates" vs state-of-the-art LLM planners (measurement = success rate, not edit statistics) — [arXiv PDF](https://arxiv.org/pdf/2308.13724)
- **CoPAL** ("Corrective Planning of Robot Actions with Large Language Models", ICRA 2024, arXiv:2310.07263): hierarchical multi-level feedback loop that replans on "physically grounded, logical, and semantic errors"; evaluated on "executability, correctness, and time complexity" in blocks world, barman, pizza-preparation — [arXiv html](https://arxiv.org/html/2310.07263v3)
- **AutoTAMP** (ICRA 2024): uses re-prompting with syntactic and semantic *error feedback* from the STL checker to the LLM translator rather than editing the plan directly — [survey description](https://arxiv.org/html/2505.05762v1)
- **LLM-Modulo**: critics "backprompt the LLM for fixing known issues" — repair is always delegated back to the LLM — [arXiv html](https://arxiv.org/html/2402.01817)
- **Hierarchical Planning with Knowledge-Graph RAG and Symbolic Verification** (arXiv:2504.04578) "employs backprompting with LLMs to correct plans using feedback from symbolic validators, addressing errors by adjusting preconditions and postconditions or modifying action sequences" — [arXiv PDF](https://arxiv.org/pdf/2504.04578)
- **Grounded Evaluation and Repair for NL-to-PDDL Problem Generation** (arXiv:2609.09898, 2026) builds an explicit pipeline of "PDDL parsing, planning and validation, a domain-conformance checker, an LLM critic, and iterative repair" — repair of the *problem spec*, not the plan — [arXiv html](https://arxiv.org/html/2609.09898)
- **ReplanVLM** (IEEE RA-L 2024, arXiv:2407.21762) distinguishes *internal* error correction (pre-execution check of generated code for errors/hallucinations, corrections fed back for modified planning) from *external* error correction (compare pre-/post-execution environment states, identify failure cause, replan); reports average error *detection* rate 95.7% and error *correction* rate 80% — [arXiv](https://arxiv.org/abs/2407.21762); [IEEE Xplore](https://ieeexplore.ieee.org/document/10700686/)
- **EvoPlan** (arXiv:2607.06724, 2026) is the clearest "LLM repairs, validator selects" design: LLMs "propose and repair plans against a fixed PDDL problem, with programmatic validators deciding which ones survive" — [arXiv html](https://arxiv.org/html/2607.06724)
- On metrics: "Chasing Progress, Not Perfection" (arXiv:2412.10675) observes that LLM-planner evaluation has "primarily focused on the validity rate of the generated plans" and argues validity rate alone "is inadequate for differentiating between the performances of various strategies" — [arXiv PDF](https://arxiv.org/pdf/2412.10675)

### Inferences
- A taxonomy for the thesis write-up: (1) **re-prompt repair** (ISR-LLM, CoPAL, AutoTAMP, LLM-Modulo, ReplanVLM internal, Safety Chip) — the LLM is both proposer and repairer; (2) **reject-and-replan** (SayCan step gating effectively discards and re-proposes; KnowNo escalates to a human); (3) **symbolic/minimal repair by a classical module** — the Fox-et-al. tradition, essentially absent from the LLM-robot literature. A classical M3 that performs *deterministic minimal edits* (swap, clamp, default) to a VLM plan occupies the empty third cell.
- Edit distance *is* an established formal notion for this (plan stability = action-set difference between original and repaired plan), so the thesis can measure repair magnitude with a 20-year-old metric that no LLM-robot paper currently reports.

### Gaps
- No LLM/VLM-robotics paper found that reports plan-stability/edit-distance between the model's proposal and the executed plan; the metric exists only in the classical repair literature.
- Could not establish any paper where a *non-LLM* module performs the repair of an LLM-proposed robot plan (the closest is temporal-logic control synthesis in RoboGuard, Q3, which re-synthesizes rather than minimally edits).

## Key Question 3: Safety shields / runtime monitors for LLM-driven robot actions, especially multi-robot

### Takeaway
Shields come in three layers: (i) plan-level logic shields that check or re-synthesize LLM plans against LTL specs (Safety Chip, RoboGuard, VerifyLLM); (ii) execution-level safety filters (CBFs, predictive safety filters) that minimally modify commanded controls, recently parameterized by VLMs; (iii) monitor-and-veto agents (ProbGuard, LabGuard, SafeGate). RoboGuard is the flagship quantitative result (unsafe-plan execution 92% → <3%). Dedicated *multi-robot* LLM shields are still thin; multi-robot CBF work and LLM work have not fully merged.

### Cited Findings
- **Plug in the Safety Chip: Enforcing Constraints for LLM-driven Robot Agents** (ICRA 2024, arXiv:2309.09919): "translates natural language to LTL formulas, monitors the agent's decision-making process, and reprompts with reasons for violation for re-planning" — a queryable LTL safety-constraint module bolted onto an LLM agent — [arXiv PDF](https://arxiv.org/pdf/2309.09919)
- **RoboGuard** ("Safety Guardrails for LLM-Enabled Robots", arXiv:2503.07885, accepted IEEE RA-L Feb 2026): two stages — (1) a root-of-trust LLM grounds predefined safety rules into the robot's environment as temporal-logic specifications via chain-of-thought; (2) temporal-logic *control synthesis* "resolves potential conflicts between these contextual safety specifications and a possibly unsafe plan... while minimally violating user preferences." Under worst-case jailbreaking attacks it "reduces the execution of unsafe plans from over 92% to below 3% without compromising performance on safe plans" — [arXiv](https://arxiv.org/abs/2503.07885); [RA-L preprint PDF](https://arxiv.org/pdf/2503.07885)
- **CBF shields (control layer)**: in multi-robot safe-control taxonomy, "a CBF-based shield outputs a control solution that minimally modifies the nominal control input while guaranteeing safety, where the nominal policy may come from a learning-based approach without safety considerations"; CBFs sit alongside Predictive Safety Filters and Hamilton-Jacobi reachability — "Learning Safe Control for Multi-Robot Systems: Methods, Verification, and Open Challenges" (arXiv:2311.13714) — [arXiv html](https://arxiv.org/html/2311.13714); the survey also covers centralized and distributed barrier-certificate learning for multi-agent systems and the scaling challenge — same source
- **VLM-parameterized CBFs**: "Dynamic Control Barrier Function Regulation with Vision-Language Models for Safe, Adaptive, and Realtime Visual Navigation" (arXiv:2603.21142, 2026) uses egocentric RGB + a VLM to "adapt the conservativeness of a CBF safety filter in real time by producing a risk estimate that dynamically updates CBF parameters" — [arXiv html](https://arxiv.org/html/2603.21142v1); "Multi-Link Safety Filtering for VLA Policies Around Moving Hazards" (arXiv:2609.40007, 2026) applies safety filtering to vision-language-action policies — [arXiv html](https://arxiv.org/html/2609.40007)
- **Language-updated safety sets**: "Updating Robot Safety Representations Online from Natural Language Feedback" (arXiv:2409.14580) — [arXiv PDF](https://arxiv.org/pdf/2409.14580)
- **Monitor agents**: **ProbGuard** ("Proactive Runtime Monitoring for LLM Agent Safety via Probabilistic Prediction", arXiv:2508.00500) "anticipates safety violations through probabilistic risk prediction" rather than reacting post-hoc — [arXiv html](https://arxiv.org/html/2508.00500); **LabGuard** (arXiv:2606.31045, 2026) grounds natural-language lab rules into runtime guards for embodied lab agents — [arXiv PDF](https://arxiv.org/pdf/2606.31045); **SafeGate**-style "Pre-Execution Safety Gate & Task Safety Contracts" (arXiv:2604.05427, 2026) frames an invariant-based runtime shield for LLM systems — [arXiv PDF](https://arxiv.org/pdf/2604.05427)
- **Uncertainty gate as a shield**: **KnowNo** ("Robots That Ask For Help: Uncertainty Alignment for Large Language Model Planners", CoRL 2023, arXiv:2307.01928) uses conformal prediction over LLM option scores; "if there is more than one option in the [prediction] set, the robot asks for help," giving statistical guarantees on task completion while minimizing human intervention, with no fine-tuning — [PMLR v229](https://proceedings.mlr.press/v229/ren23a.html); [project page](https://robot-help.github.io/)
- **Multi-robot threat angle**: "When Coordination Becomes a Threat: Communication Attacks in LLM-Controlled Multi-Robot Systems" (arXiv:2608.06830, 2026) studies adversarial inter-robot messages — evidence that the multi-robot LLM safety sub-field is forming — [arXiv PDF](https://arxiv.org/pdf/2608.06830); broader context in "A Comprehensive Survey on Physical Risk Control in the Era of Foundation Model-enabled Robotics" (arXiv:2505.12583) — [arXiv PDF](https://arxiv.org/pdf/2505.12583) and "Trust in LLM-controlled Robotics: a Survey of Security Threats, Defenses and Challenges" (arXiv:2601.02377, 2026) — [arXiv PDF](https://arxiv.org/pdf/2601.02377)

### Inferences
- RoboGuard's "minimally violating user preferences" control synthesis is the nearest published relative of "minimal repair" — but it synthesizes a compliant plan rather than itemizing and logging which legs of the LLM plan were kept, altered, or defaulted.
- For the thesis, M4's safety invariants (min distance, speed limits) map onto the CBF/shield layer; M3's leg audit maps onto the plan-level logic-shield layer. Published systems rarely have both layers *and* report what each layer rejected.

### Gaps
- No paper found that runs a plan-level shield over a *VLM-proposed multi-robot* plan in warehouse-style navigation; shields are either single-robot (RoboGuard, Safety Chip) or multi-robot-but-not-LLM (CBF literature).
- 2026-preprint shields (SafeGate, LabGuard, ProbGuard) have unverified venue status.

## Key Question 4: Novelty check — does any published system report "how much of the model's plan survived verification" as a first-class metric?

### Takeaway
Partial precedents exist — stage-wise validity rates (ViLaIn), detection/correction rates (ReplanVLM), unsafe-plan-execution rates under a shield (RoboGuard), back-prompt iteration counts (LLM-Modulo-style loops), and classical plan stability (Fox et al.) — but I found **no published system that logs per-leg provenance (verbatim / repaired / defaulted) of a model-proposed plan and reports it as a first-class experimental quantity**. The closest analogues each capture one slice of this.

### Cited Findings
- **Whole-plan validity rates are the standard metric**: PlanBench (arXiv:2206.10498) "formalizes evaluation in PDDL, enabling mechanical verification of plan validity"; GPT-4 averaged ~12% executable-plan success across domains, and in "LLMs Still Can't Plan; Can LRMs?" (arXiv:2409.13373) o1-preview reaches 97.8% on 3–5-block Blocksworld but 23.63% on 20–40-step instances — [arXiv](https://arxiv.org/abs/2409.13373); [PlanBench overview](https://www.emergentmind.com/topics/planbench)
- "Chasing Progress, Not Perfection" (arXiv:2412.10675) explicitly criticizes validity rate as "too stringent for evaluating incremental improvements in plan quality" — i.e., the field itself notes the absence of finer-grained survival metrics — [arXiv PDF](https://arxiv.org/pdf/2412.10675)
- **Stage-wise survival, closest precedent #1 — ViLaIn**: reports syntactic correctness >99% vs. valid plans >58% — a two-stage "how much survived each gate" statistic for problem generation, though not leg-level and not about repair provenance — [ViLaIn ICRA 2024 PDF](https://www.lsta.media.kyoto-u.ac.jp/publications/shirai-ICRA2024.pdf)
- **Closest precedent #2 — ReplanVLM**: reports error detection rate (95.7% avg) and error correction rate (80% avg) as headline numbers — repair *success* statistics, but not what fraction of the original plan was preserved — [arXiv](https://arxiv.org/abs/2407.21762)
- **Closest precedent #3 — RoboGuard**: reports fraction of unsafe plans executed before vs after the guardrail (92% → <3%) — a plan-survival-under-shield number, but binary per plan, not per leg, and with no verbatim/repaired/default breakdown — [arXiv](https://arxiv.org/abs/2503.07885)
- **Closest precedent #4 — classical plan stability**: Fox et al. (ICAPS 2006) define stability as the difference between original and repaired plan and evaluate repair vs replanning on it — the formal ancestor of a "fraction of plan preserved" metric, predating LLMs — [Strathprints PDF](https://strathprints.strath.ac.uk/2776/1/strathprints002776.pdf)
- Graph Edit Distance between plan topologies and "Plan Stability measuring the fraction of non-target nodes unchanged after revision" appear as evaluation constructs in recent LLM-agent planning evaluation discussions (human-LLM collaborative planning, arXiv:2605.23023) — text-domain, not embodied — [arXiv PDF](https://arxiv.org/pdf/2605.23023)
- Repair-loop papers measure *iterations/success*, not preservation: ISR-LLM reports success-rate gains from its validator loop — [arXiv PDF](https://arxiv.org/pdf/2308.13724); LLM-Modulo implementations report back-prompting rounds in case studies (travel planning) — [arXiv html](https://arxiv.org/html/2405.20625v1)

### Inferences
- The thesis's provenance-logging metric (per-leg verbatim/repaired/default counts over a VLM-proposed multi-robot plan) appears to be a genuine measurement-level novelty: the components exist separately (stage-wise validity, correction rates, plan stability) but no embodied-planning paper unifies them, and none treats provenance as a *reported experimental quantity* rather than an internal mechanism.
- Framing tip: position the metric as "plan stability (Fox et al. 2006) transplanted to the LLM-proposer setting, refined to a three-way provenance label" — this both cites precedent and sharpens the novelty claim against the obvious reviewer objection.

### Gaps
- Absence of evidence is not proof of absence: searches covered plan-validity/repair-metric phrasings, but a system could report such statistics under different vocabulary (e.g., "intervention rate", "override rate" in HRI or autonomous-driving stacks). A targeted check of "override/intervention rate" literature in AV safety could further harden the claim.
- RoCo (Q5) tracks re-plan attempts during its feedback loop; whether its paper tables report replan counts as a headline metric was not verified this session — worth reading the RoCoBench tables directly before claiming priority over it.

## Key Question 5: Execution-feedback loops — feeding succeeded/failed legs back into the next model invocation, especially multi-robot

### Takeaway
Single-robot closed loops are canonical (Inner Monologue, DoReMi, Reflexion as the text-side pattern); the multi-robot versions (RoCo, COHERENT's PEFA cycle, MHRC, DEXTER-LLM, event-driven hierarchical teams) all re-prompt a (usually centralized) LLM with execution outcomes and environment feedback, and the literature now explicitly finds centralized LLM coordination superior in success rate and token efficiency — directly supporting the thesis's centralized-VLM-coordinator framing.

### Cited Findings
- **Inner Monologue** (CoRL 2022, arXiv:2207.05608) established the pattern: success detection, scene description, and human feedback are injected as text into the LLM's prompt loop so it can retry or replan (from author's prior knowledge, ID unverified this session) — [arXiv](https://arxiv.org/abs/2207.05608)
- **DoReMi** ("Grounding Language Model by Detecting and Recovering from Plan-Execution Misalignment", arXiv:2307.00329; Guo, Wang, Zha, Chen): the LLM "generates constraints that can indicate misalignment during execution," a VLM "detect[s] constraint violations continuously," and on violation the LLM is immediately called to replan; shown on robot arms and humanoids with higher success rates and shorter completion times — [arXiv](https://arxiv.org/abs/2307.00329)
- **Reflexion** (NeurIPS 2023, arXiv:2303.11366): text-domain contrast — verbal self-feedback stored in episodic memory improves subsequent trials; no external verifier, so correctness is self-judged (from author's prior knowledge, ID unverified this session) — [arXiv](https://arxiv.org/abs/2303.11366)
- **RoCo** ("Dialectic Multi-Robot Collaboration with Large Language Models", ICRA 2024, arXiv:2307.04738): LLMs do both inter-robot dialogue and waypoint planning; "the system provides feedback from the environment, such as collision checking, and prompts LLM agents to improve their plan and waypoints in-context" — an explicit verify-and-re-prompt loop over multi-robot motion, with IK/collision checks as the verifier — [arXiv html](https://arxiv.org/html/2307.04738)
- **COHERENT** ("Collaboration of Heterogeneous Multi-Robot System with Large Language Models", ICRA 2025, arXiv:2409.15146): "multiple Proposal-Execution-Feedback-Adjustment (PEFA) cycles between a centralized task assigner and individual robot executors" — execution outcomes flow back to the central LLM each cycle — [arXiv html](https://arxiv.org/html/2409.15146v3)
- **MHRC** (arXiv:2409.16030): "closed-loop decentralized multi-heterogeneous robot collaboration," integrating feedback tied to robot capabilities into LLM decision-making — [arXiv PDF](https://arxiv.org/pdf/2409.16030)
- **DEXTER-LLM** (arXiv:2508.14387): dynamic, explainable multi-robot coordination in unknown environments with online task updates — [arXiv html](https://arxiv.org/html/2508.14387v1); **CoMuRoS**-style hierarchical teams add *event-driven replanning* by a Task Manager LLM (arXiv:2511.22354, 2026) — [arXiv html](https://arxiv.org/html/2511.22354v2); **CLiMRS** (arXiv:2602.06967, 2026) runs a grouping–planning–execution–feedback loop with "feedback from both robot execution outcomes and environment changes" — [arXiv html](https://arxiv.org/html/2602.06967)
- **Centralized vs decentralized evidence**: "Centralized methods, where a single LLM handles planning, have been proven superior in terms of success rate and token efficiency," and decentralized dialogue scales poorly as robots/rounds grow due to prompt-length blowup (IMR-LLM, arXiv:2603.02669, summarizing the comparison line of work incl. SMART-LLM, arXiv:2309.10062, the representative centralized planner) — [arXiv html](https://arxiv.org/html/2603.02669); survey context: "Large Language Models for Multi-Robot Systems: A Survey" (arXiv:2502.03814) — [arXiv html](https://arxiv.org/html/2502.03814v5)
- **LERa** ("Replanning with Visual Feedback in Instruction Following", arXiv:2507.05135): VLM-side replanning triggered by visual feedback during instruction following — [arXiv html](https://arxiv.org/html/2507.05135); scene-graph-guided *proactive* replanning before failures manifest: arXiv:2508.11286 — [arXiv PDF](https://arxiv.org/pdf/2508.11286)

### Inferences
- The thesis loop (M5 feeds congestion events + leg outcomes back into the next VLM invocation; M3/M4 verify) is a COHERENT/PEFA-shaped architecture with the critical difference that the feedback consumer is a *VLM over an annotated scene image* rather than a text-state LLM, and the verifier is a deterministic grounding module rather than another LLM round.
- RoCo is the single most important related work to cite and differentiate: it already closes the multi-robot propose-verify loop with collision checking, but the LLM repairs its own plan via re-prompting (expensive, unbounded), whereas a classical M3 repair is deterministic, bounded, and auditable.

### Gaps
- Quantitative replan-count or feedback-efficacy tables for RoCo/COHERENT were not extracted this session; read the papers' experiment sections before making comparative claims.
- No found system feeds *per-leg* success/failure provenance (as opposed to whole-task or whole-step outcomes) into the next VLM call; unclear whether this is unexplored or just unreported.
